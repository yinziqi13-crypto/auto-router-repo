## ADR-001：增强层采用"前置薄代理"而非"改 New API 源码/插件"

**Status**：Accepted

### Context

New API（one-api fork）作为基座提供 OpenAI 兼容协议、渠道管理、令牌/用户/额度扣减、计费倍率、调用日志等能力。但它没有上游额度感知能力——不知道哪些渠道的免费额度耗尽了，也不会自动下线耗尽的渠道。

需要增加一个"额度感知层"来解决：免费额度优先路由 → 耗尽自动降级到付费渠道 → 耗尽后自动冷却恢复。

### Options Considered

1. **Fork 改 New API 源码**：直接在 Go 代码里加额度逻辑
2. **直连上游**：Python 增强层直接调腾讯/百炼 API，绕过 New API
3. **前置薄代理**：Python 进程做前置代理，经 New API 管理接口交互，不改源码

### Decision

选 3 — 前置薄代理。

### Rationale

- New API AGPL-3.0 协议，改源码有合规风险
- rc.30 还在快速迭代，改源码每次升级都要 merge conflict
- 团队无 Go 能力，自研资产全在 Python（tc_cloud.py / ai_router.py）
- 直连上游会丢失 New API 的计费日志、协议转换、传输层重试能力
- 前置代理只加决策不碰字节流，流式响应管道透传，单请求增强层开销 < 5ms

### Consequences

- ✅ 升级 New API 无耦合
- ✅ 协议合规（不改 AGPL 源码）
- ✅ 复用团队 Python 技能
- ❌ 多一跳延迟（< 5ms，实测可接受）
- ❌ 多一个进程要运维（M3-1 systemd 解决）

### Implementation Evidence

- M1-1 ~ M1-6：FastAPI 骨架编码 + 部署 + 五场景验证全部通过
- M2-6：Provider 抽象框架落地，adapter.py 继承 NewAPIProvider，transport 可插拔
- 实测延迟：非流式请求 874ms（含上游响应），增强层决策开销 < 1ms

## ADR-002：free/paid 分流用"双 token 方案"，不依赖 New API group 机制

**Status**：Accepted（2026-09-03 M1-0 实测后裁决，2026-09-04 孙磊拍板）

### Context

需要实现"免费优先"：优先走免费渠道（ch3 tencent-free / ch4 bailian-free），免费额度耗尽后降级到付费渠道（ch1 tencent-plan / ch2 bailian-lite）。

最初设计想用 New API 的 group 机制：token.group=free → 渠道挂 group=free → 路由到免费渠道。

### Options Considered

1. **New API group 机制**：token 绑定 group，渠道挂对应 group
2. **双 token 方案**：token-free 和 token-paid 两个令牌，增强层选 token 转发
3. **动态改 priority**：每次请求改 abilities 表的 priority 值

### Decision

选 2 — 双 token 方案。

### Rationale

- M1-0 实测：rc.30 自定义 group 路由不可用。token.group=free + 渠道挂 group=free → 403 无权访问
- 用户级分组权限只认 default 等内置组
- 请求级 body.group 仅在 /pg/ 路径生效，普通 /v1/ 路径不支持
- 动态改 priority = 写放大 + 竞态，channels/abilities 同步是坑（M0 实测教训）
- 双 token 是读路径操作：增强层选 token → 换 Authorization 头 → 转发，零写操作

### Mechanism

- token-free（auto-router-free, id=2）：group=default，New API 按模型名路由到 free 渠道（ch3/ch4，priority=5）
- token-paid（auto-router-paid, id=3）：group=default，但 ch1 的模型名是 deepseek-v4-flash-202605（通过 model_mapping 映射），priority=10
- 增强层 decision.py 根据 QuotaState 选 token：
  - free 渠道可用 → token-free + 模型名 deepseek-v4-flash → New API 路由到 ch3/ch4
  - free 渠道全 exhausted → token-paid + model_mapping 转 deepseek-v4-flash-202605 → New API 路由到 ch1
- **关键发现**：token 不控制路由，模型名才是路由控制器。model_mapping 控制发送哪个模型名给 New API → 控制路由到 free 还是 paid

### Consequences

- ✅ 不依赖 rc.30 未文档化的 group 机制，方案稳定可预期
- ✅ 零写操作，无竞态风险
- ❌ 多一个 token 管理维度（可接受，token 在 New API 控制台创建一次）

### Implementation Evidence

- M1-0：group 机制验证失败（403），双 token 方案确认
- M1-6 场景三：token-paid + model_mapping → ch1 命中，实测通过
- M1-6 场景四：全 free exhausted → 自动降级 paid → ch1 命中，实测通过
- config.json free_providers 显式列表替代名字匹配，不依赖渠道名含 "free"

### P0-6 补充：selected_provider 语义说明

**实测发现**：Auto Router 的 `selected_provider` 是决策意图（选哪个 pool），不等于 New API 实际执行的渠道。M0 实测数据显示，free token 请求有 13% 命中付费渠道，paid token 有 20% 命中免费渠道——这是 New API 在同 group 内按 priority/weight 路由的正常行为，不是 bug。

**决策**：M2.5 不改字段名（避免 DB schema 变更），M3 看板迭代时将 `selected_provider` 改名为 `selected_pool`，语义对齐。过渡期看板加注「决策池分布，非实际执行渠道」。

### 模型名隔离约束

free/paid 隔离的唯一机制是模型名 + model_mapping：

- `deepseek-v4-flash` → free 渠道（ch3/ch4 持有此模型名）
- `deepseek-v4-flash-202605` → paid 渠道（ch1 独占）
- model_mapping 在用 paid token 时将 `deepseek-v4-flash` → `deepseek-v4-flash-202605`
- 任何 model_routes 映射或容错匹配改动，必须确认目标模型名在正确的池里

## ADR-003：额度状态采用"事件驱动 + 定时同步"双源，探针只做恢复确认

**Status**：Accepted

### Context

New API 无额度查询 API（M0 实测 404）。耗尽的模型不会自动下线。需要知道哪些渠道的免费额度什么时候耗尽了，才能触发降级。

### Options Considered

1. **纯被动 402**：只靠用户请求遇到 402 后才知道额度耗尽
2. **纯主动查询**：定时调腾讯云控制台 API 查额度
3. **事件驱动 + 定时同步**：402 事件为第一信号源，tc-cloud-sync 为水位数据源，探针仅用于恢复确认

### Decision

选 3 — 事件驱动 + 定时同步双源。

### Rationale

- 纯被动：首次耗尽必然被用户遇到一次，体验差
- 纯主动：腾讯云控制台数据有同步延迟，不实时
- 双源：402 实锤事件 > tc-cloud-sync 主动数据 > 探针推断，优先级仲裁明确
- 402 报文 100% 可识别（M0 实测）
- 探针不浪费真实流量试探，只在耗尽后的冷却恢复时做最小代价探测（1 次 5-token 调用）

### State Machine

```
unknown → available（首次成功）
available → exhausted（连续 3 次 402 事件，record_402 累计 consecutive_402 >= 3）
exhausted → available（冷却到期，cooldown_scan() 每 60s 自动重置）
exhausted → exhausted（冷却未到期，继续等待；下次 402 会再 record_402，cooldown ×2 指数退避，上限 24h）
available → suspected_low（tc-cloud 报低水位，预留，当前未实现）
suspected_low → exhausted（402 实锤）
```

**关键实现细节（与原设计的偏差）：**

1. **3 次门槛**：原设计写"402 事件 → exhausted"，实际代码 `record_402()` 在 `consecutive_402 >= 3` 时才标记 EXHAUSTED。理由：单次 402 可能是瞬时抖动，3 次连续才确认为耗尽。
2. **无探针恢复**：原设计写"探针只做恢复确认"，实际代码未实现探针。冷却到期后 `cooldown_scan()` 直接重置为 AVAILABLE，不做探测调用。理由：避免浪费真实流量，冷却期已经足够覆盖免费额度重置周期。
3. **无 200 清错误计数**：原设计写"200 → 清错误计数"，实际代码 `reset()` 只在冷却恢复时调用，请求成功时不重置 `consecutive_402`。这是已知偏差，M3 补充成功回写逻辑。

### Consequences

- ✅ 不浪费真实流量试探
- ❌ 首次耗尽必然被用户遇到一次（用增强层 402 重试兜住）
- ⚠️ 无 200 回写：连续 2 次 402 后恢复，第 3 次请求成功不会清零计数，下次 402 会直接到 3 次。M3 补充。

### Implementation Evidence

- M2-2：record_402() 指数退避 1h→2h→4h→24h 上限，3 次门槛标记 EXHAUSTED
- M2-2：cooldown_scan() 每 60s 自动扫描，冷却到期直接重置（无探针）
- M2-2：冷启动 _restore_from_db() 恢复 cooldown_until（修复了原实现漏恢复的 bug）
- M1-6 场景四：手动标记 exhausted → 验证降级逻辑正确
- M1-6 场景五：清空状态 → 恢复 free 路由正确

### Deviation from Original Design

| 原设计 | 实现 | 理由 |
|--------|------|------|
| 单次 402 → exhausted | 连续 3 次 402 → exhausted | 避免瞬时抖动误判 |
| 探针确认恢复 | 冷却到期直接恢复 | 避免浪费流量 |
| 200 清错误计数 | 未实现成功回写 | M3 补充 |
| 冷却 24h 起步/72h 上限 | 1h 起步/24h 上限 | 更快恢复，覆盖重置周期 |

### 五态候选池选择（M2.5 新增）

决策引擎 `_select_pool()` 按候选池状态分五态选择 provider 与 token 类型：

| 态 | 条件 | token | fallback | error_code |
|---|---|---|---|---|
| A | 有可用 free 候选（非全 exhausted） | free | None | — |
| B | free 全 exhausted + 有 paid 候选 | paid | exhausted_skip | — |
| C | 无 free 候选 + 有 paid 候选 | paid | paid_only | — |
| D | free 全 exhausted + 无 paid 候选 | — | — | 503 |
| E | 无候选（模型不在任何 provider_models） | — | — | 404 |

**C 态修复要点（M2.5）**：token 类型从「最终候选池」推导，不再从「是否 all_free_exhausted」间接推断。旧逻辑在 C 态（模型只在 paid 池）误判 token=free，导致用 free 令牌请求 paid-only 模型。实测证据：

```
model=deepseek-v4-pro  provider=tencent_plan  token=paid  fallback=paid_only  ← 修复后正确
```

## ADR-004：增强层仅对"额度耗尽"做 1 次请求级重试，其余交给 New API

**Status**：Accepted

### Context

New API 原生 RetryTimes=2 处理传输层重试（连接失败/5xx），但不跨模型池重试。402（额度耗尽）触发 New API 内部重试，但候选池内无兜底则透传 402 给调用方。

需要增强层在 402 场景做请求级重试，切到付费渠道。

### Options Considered

1. **增强层全权重试**：所有错误类型都由增强层重试
2. **New API 全权重试**：不改增强层，靠 New API 内部重试
3. **职责切分**：传输层归 New API，额度层归增强层，各重试一次

### Decision

选 3 — 职责切分。

### Rationale

- 402 不跨模型池（M0 实测）：New API 在 free 渠道池内找不到可用渠道时直接透传 402，不会自动切到 paid 池
- 400 不重试直接失败（M0 实测）：无效模型名是配置错误，重试无意义
- 5xx/连接失败：New API RetryTimes=2 已覆盖，增强层不重复造轮子
- 增强层重试仅在"首次免费命中额度耗尽"场景，换 token-paid 重试 1 次

### Error Classification

| HTTP Code | 谁处理 | 重试策略 |
|-----------|--------|----------|
| 200 | — | 成功（注：当前未实现清零 consecutive_402，M3 补充成功回写） |
| 402 | 增强层 | record_402() 累计计数，连续 3 次标记 exhausted → 换 token-paid 重试 1 次 |
| 400 | 不重试 | 透传错误（model_mapping 缺条目，告警） |
| 5xx | New API | RetryTimes=2 内部重试 |
| 连接失败 | New API | RetryTimes=2 内部重试 |

### Consequences

- ✅ 最坏情况单请求 2 次上游调用（时延可控）
- ✅ 职责清晰，错误分类表明确
- ❌ 两套重试逻辑需要维护（Decision Engine + New API RetryTimes）

### Implementation Evidence

- M1-6 场景四：free 渠道全 exhausted → 增强层自动换 token-paid → 重试命中 ch1，实测通过
- M1-6 双重调用修复：流式请求走 decide() + forward_stream() 单次调用，不再双重消耗额度
- M1-6 降级逻辑一致性修复：decide() 和 route() 共用 _free_pool_check()，流式和非流式降级逻辑一致

## ADR-005：selected_provider 字段改名为 selected_pool（P0-6 方案）

**Status**：Accepted（2026-09-05 决策，实现延 M3）

### Context

M0 实测数据显示，Auto Router 决策引擎的 `selected_provider` 字段记录的是"选哪个 pool"（tencent_free / bailian_free / tencent_plan / bailian_lite），而非 New API 实际执行的渠道（ch1~ch4）。

实际路由由 New API 在同 group 内按 abilities 表 priority/weight 决定，Auto Router 只控制：
1. 用哪个 token（free/paid）→ 隔离 free 池和 paid 池
2. 发什么模型名（model_mapping）→ 控制走哪个上游

因此 `selected_provider` 这个名称有误导性——它暗示"选中了 New API 的某个渠道/provider"，但实际上只表达了"选了哪个 pool 级别"。M0 数据中 free token 有 13% 命中付费渠道、paid token 有 20% 命中免费渠道，这不是 bug，而是 New API 在 token 可访问范围内自由路由的正常行为。

**泄漏触发条件（M2.5 实测确认）**：当同一个模型名（如 `deepseek-v4-pro`）同时出现在 free 渠道（如 bailian-free 挂了 141 个模型）和 paid 渠道时，New API 在 token 可访问范围内按 priority/weight 自由路由，可能命中 free 渠道而非 intended paid 渠道。对照组：`deepseek-v4-flash` 无泄漏，因为 paid 渠道挂的是 `deepseek-v4-flash-202605`（带后缀，名字不重叠）。**泄漏只发生在跨池同名的模型上。**

**修复方向（方案 A，已决策）**：对跨池同名的 paid-only 模型加后缀（如 `deepseek-v4-pro` → `deepseek-v4-pro-paid`），靠 model_mapping 保证名字不重叠。已有 `deepseek-v4-flash` → `deepseek-v4-flash-202605` 的成功先例。M3-2 执行。

### Decision

1. **M2.5 不改字段名**：避免 DB schema 变更（router_decision_event 表已有多条历史记录，改列名会导致历史数据不兼容）
2. **M3 实施改名**：将 `selected_provider` → `selected_pool`，DB schema + API 响应 + 看板字段全部对齐
3. **过渡期看板标注**：dashboard.html 的 provider 分布饼图标题加注「决策池分布，非实际执行渠道」
4. **ADR-002 补充**：在 ADR-002 的 P0-6 补充说明中明确 `selected_provider` 为决策意图

### Rationale

- 历史数据兼容：M0 已积累决策日志，改字段名需 migration，M2.5 修复窗口不够
- 语义准确性：`pool` 比 `provider` 更准确地描述 Auto Router 的控制粒度
- 看板已过渡处理：加注说明消除了歧义，不阻塞 M2.5 上线
- 实现不阻塞：改名是纯展示层 + DB schema 变更，不影响路由逻辑

### Migration Plan（M3 执行）

```
步骤 1: ALTER TABLE router_decision_event RENAME COLUMN selected_provider TO selected_pool;
步骤 2: 更新 models.py 中 RouterDecisionEventRecord 的字段名
步骤 3: 更新 decision.py 中所有 selected_provider 引用为 selected_pool
步骤 4: 更新 dashboard.html 字段引用
步骤 5: 更新 API 响应 JSON 字段名（向后兼容期：同时返回两个字段名，1 个版本后移除旧名）
步骤 6: 更新运维手册中所有引用
```

### Consequences

- ✅ M2.5 无 DB schema 变更风险，过渡期看板标注已消除歧义
- ✅ M3 改名后语义清晰，新接入者不会误解
- ❌ M3 需一次 migration + 全量代码改名（影响面：decision.py / models.py / dashboard.html / 运维手册）

### Implementation Evidence

- M2.5：过渡期看板标注已实施（dashboard.html 标题改为「决策池分布，非实际执行渠道」）
- ADR-002 P0-6 补充说明已写入整合版
- 改名实现列入 M3 任务清单

## 红线（不可违背）

1. **不改 New API 源码** — AGPL-3.0 规避 + 升级自由度
2. **不直连上游** — 所有模型流量经 New API，保证计费日志/协议转换/重试完整（M3 开始按需开放直连）
3. **不直写 New API 的 SQLite** — 只走管理 API，避免 channels/abilities 不同步
