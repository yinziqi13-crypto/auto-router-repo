## 一、router.db 数据模型设计

### 1.1 设计原则（架构决策）

| 原则 | 说明 | 权衡 |
|---|---|---|
| **物理隔离** | router.db 与 New API 的 one-api.db **完全独立**，不共享连接 | ✅ 红线 3 遵守（不许直写 New API SQLite）；❌ 两份数据一致性靠事件回写，不靠事务 |
| **可再生缓存** | QuotaState / ErrorEvent 是**缓存不是数据源**；数据源是：① tc-cloud-sync 腾讯云控制台数据 ② 402 事件被动感知 | ✅ 状态表损坏可从 tc-cloud-sync 全量重建（<5min）；❌ 不存永久业务数据 |
| **append-only 事件流** | ErrorEvent / RouterDecisionEvent **只追加不修改**，破案靠日志 | ✅ 事件溯源；❌ 存储稍大（可接受，SQLite 足够） |
| **内存优先** | QuotaState 热数据全量加载内存，SQLite 只做持久化和事件溯源 | ✅ 单请求增强层开销 < 5ms；❌ 多实例需换 Redis（V5.0） |

### 1.3 QuotaState（额度状态表）—— 核心聚合

**粒度**：(provider_id, model)  
**主键**：(provider_id, model)  
**说明**：一个逻辑的"模型+供应商"组合的状态快照

| 字段 | 类型 | 约束 | 说明 | 来源 |
|---|---|---|---|---|
| provider_id | TEXT | PK, FK → Provider.id | tencent-free / tencent-plan / bailian | 手动配置 |
| model | TEXT | PK | 逻辑模型名（如 deepseek-v4-flash） | 手动配置 |
| quota_status | TEXT | NOT NULL, DEFAULT 'unknown' | **available** / suspected_low / **exhausted** / unknown | 见 1.4 状态机 |
| exhausted_at | DATETIME | NULL | 首次观测到 402 的时刻 | 402 事件 |
| error_status | TEXT | NOT NULL, DEFAULT 'none' | none / cooldown / probing / circuit_open | 状态机 |
| cooldown_until | DATETIME | NULL | 冷却截止时间（指数退避） | 状态机 |
| consecutive_errors | INT | NOT NULL, DEFAULT 0 | 连续错误计数（成功清零） | 结果回写 |
| health_score | INT | NOT NULL, DEFAULT 100 | 0-100 综合评分 | 见 1.5 健康评分 |
| last_success_at | DATETIME | NULL | 最近一次成功调用 | 结果回写 |
| source_of_truth | TEXT | NOT NULL, DEFAULT 'passive_402' | tc_cloud_sync / event_402 / probe | 冲突仲裁 |

**索引**：
- INDEX idx_quota_status ON QuotaState(quota_status) —— 快速查"所有耗尽模型"
- INDEX idx_health_score ON QuotaState(health_score) —— 快速选最高分渠道

**内存结构**（Python dataclass，启动时全量加载）：
```python
@dataclass
class QuotaStateRow:
    provider_id: str
    model: str
    quota_status: str  # available / suspected_low / exhausted / unknown
    exhausted_at: datetime | None
    error_status: str  # none / cooldown / probing / circuit_open
    cooldown_until: datetime | None
    consecutive_errors: int
    health_score: int  # 0-100
    last_success_at: datetime | None
    source_of_truth: str  # tc_cloud_sync / event_402 / probe
```

### 1.4 QuotaState 状态机（严格 M0-M3 实测铁律）

```
                    ┌── tc-cloud报有额度/首次成功 ───→ available
                    │
                    │ probe 失败
                    ▼
unknown ──┴──────┐
                    │          │
                    │          └── tc-cloud报0 ───→ suspected_low ─── 402 ───→ exhausted
                    │                                                        │
                    │                                                        └── (T+冷却) ───→ probing ─── 探针200 ───→ available
                    │                                                                        │
                    │                                                                        └── 探针402 ───→ exhausted (冷却×2)
```

**冷却策略**（M0 实测腾讯免费额度按日/周期重置）：
- 首次耗尽冷却 **24h**（短探测无意义）
- 探针失败则 ×2 指数退避，上限 **72h**
- 恢复不靠猜：probing 用**最小代价探针**（1 次 5-token 调用），不拿真实流量试错

**状态判定优先级**（冲突仲裁，不可违背）：
1. `402 实锤事件` > 2. `tc-cloud-sync 主动数据` > 3. `探针推断`
   
**理由**：402 是上游亲口说的；控制台数据有同步延迟；探针可能遇到限流假象。

### 1.5 健康评分公式（health_score）

```
health_score = quota_weight × quota_score 
               + error_weight × error_score 
               + latency_weight × latency_score
```

| 因子 | 权重 | 分值逻辑 | 说明 |
|---|---|---|---|
| quota_score | 0.5 | available=100, suspected_low=60, exhausted=0, unknown=50 | 额度状态主导 |
| error_score | 0.3 | none=100, cooldown=40, probing=30, circuit_open=0 | 错误状态 |
| latency_score | 0.2 | 滚动 P50 延迟映射：<1s=100, 1-3s=80, 3-5s=50, >5s=20 | 未来扩展（P1） |

**当前 M1 简化**：只实现 quota_score（占 100%），error_score 和 latency_score 留字段但默认 100，P1 再激活。

### 1.6 ErrorEvent（错误事件流表）—— append-only

**用途**：402 / 500 / 400 等错误的全量溯源，不修改只追加。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT | PK, AUTOINCREMENT |
| ts | DATETIME | 错误发生时刻 |
| channel_id | INT | New API 渠道 ID |
| model | TEXT | 请求模型名 |
| http_code | INT | 402 / 500 / 400 等 |
| error_code | TEXT | 上游错误码（如 401008） |
| newapi_request_id | TEXT | 关联 New API 日志的 request ID |
| action_taken | TEXT | 触发了什么状态变更（JSON 摘要） |

**保留策略**：全量保留，SQLite 单文件 < 1GB 可存千万级事件（M1 够用）。

### 1.7 RouterDecisionEvent（决策事件流表）—— append-only，架构评审新增

**用途**：每次请求调度的完整决策记录，用于问题定位、成本归因、运营看板。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT | PK, AUTOINCREMENT |
| request_id | TEXT | 增强层生成的全链路追踪 ID（UUID） |
| ts | DATETIME | 决策时刻 |
| original_model | TEXT | 客户端原始请求模型名 |
| logical_model | TEXT | 解析后的逻辑模型名（容错/映射后） |
| task_type | TEXT | named（点名）/ auto-free（一期仅 named，预留） |
| selected_provider | TEXT | 决策选中的供应商 |
| selected_group | TEXT | free / paid（双 token 方案） |
| fallback_reason | TEXT | none / quota_exhausted / cooldown / health_down / no_candidate |
| quota_status_snapshot | TEXT | 决策时刻该模型的额度状态快照 |
| latency_ms | INT | 增强层决策耗时（不含上游） |
| newapi_request_id | TEXT | 回填：New API 侧请求 ID |
| final_channel | INT | 回填：实际命中渠道（从日志解析） |
| outcome | TEXT | success / error_402 / error_400 / error_other |

**索引**：
- INDEX idx_request_id ON RouterDecisionEvent(request_id) —— 全链路追踪
- INDEX idx_ts ON RouterDecisionEvent(ts) —— 时间范围查询

### 2.2 五大模块职责（单一职责原则）

#### 模块 1：Request Handler（入口/转发）
**文件**：`router/handler.py`  
**职责**：
- 暴露 FastAPI 端点：`POST /v1/chat/completions`
- 令牌校验（透传 New API 逻辑，不重复实现）
- 限流窗口（免费源 60 RPM 保护）
- 流式响应透传（不碰字节流，< 5ms 开销）
- 调用 Model Matcher → State Manager → Decision Engine → New API Adapter

**输入**：OpenAI 兼容请求（model / messages / max_tokens）  
**输出**：OpenAI 兼容响应（透传 New API 或增强层 402 明确报错）

**关键设计决策（ADR）**：
- 增强层是**薄代理**：只加决策，不碰字节流
- 流式响应用 `StreamingResponse` 直接管道透传（FastAPI + httpx）

#### 模块 2：Model Matcher（模型解析）
**文件**：`router/matcher.py`  
**职责**：
- 三分支解析：
  1. **点名真实模型** → 容错匹配（大小写/前缀，v3.8 逻辑迁移）→ 查 ModelCatalog 得 logical_model
  2. **`auto-free` 虚拟模型** → 任务类型识别（视觉请求→vision 池）→ 池内选可用额度中 health_score 最高的模型
  3. **僵尸/未知模型** → 回退 auto-free 逻辑（不直接报错）
- 查 ModelCatalog 获取 upstream_names（各供应商真实模型名）
- 回填 RouterDecisionEvent.original_model / logical_model

**容错匹配规则**（v3.8 遗产，一期直接迁移）：
- 大小写不敏感
- 去 vendor 前缀（如 `tencent/` 前缀去掉）
- 唯一前缀匹配（如 `deepseek-v4` 匹配 `deepseek-v4-flash`）

#### 模块 3：State Manager（状态管理）
**文件**：`router/state.py`  
**职责**：
- QuotaState 内存结构管理（加载 / 更新 / 查询）
- ErrorEvent / RouterDecisionEvent 落库（append-only）
- 冷却倒计时检查（cooldown_until <= now？）
- 探针调度（exhausted 模型恢复探测，最小代价）
- 对外提供查询接口：
  - `get_quota_state(provider_id, model) → QuotaStateRow`
  - `get_best_available_model(logical_model, task_type) → (provider_id, model) | None`

**关键设计决策（ADR）**：
- 启动时全量加载 QuotaState 到内存（SQLite → dict）
- 每次请求只做 1 次内存查询（< 1ms）
- 状态变更先更内存再落库（异步，不阻塞请求）

#### 模块 4：Decision Engine（决策引擎）
**文件**：`router/decision.py`  
**职责**：
- 核心五步决策（见第三节）：
  1. 令牌校验 + 限流
  2. 模型解析（调 Model Matcher）
  3. **额度决策**（查 State Manager，核心职责）
  4. 转发 New API（调 New API Adapter）
  5. 结果回写（调 State Manager）
- 双 token 方案实现：
  - 免费可用 → 选 `token-free`（group=free 逻辑）
  - 免费耗尽 → 按 fallback_chain 选付费供应商 → 选 `token-paid`（group=paid 逻辑）
- 回填 RouterDecisionEvent 所有字段

**决策逻辑伪代码**（M1-3 点名模型链路）：
```python
def decide(token, original_model, task_type):
    # 2. 模型解析
    logical_model, upstream_names = matcher.resolve(original_model)
    
    # 3. 额度决策（核心）
    quota = state.get_quota_state(provider_id, logical_model)
    if quota.status == 'available':
        selected_token = TOKEN_FREE
        selected_group = 'free'
    else:  # exhausted / cooldown
        # 按 fallback_chain 选下一个供应商
        next_provider = fallback_chain.next(provider_id, logical_model)
        selected_token = TOKEN_PAID
        selected_group = 'paid'
    
    # 4. 转发（先不编码，只定义接口）
    response = adapter.forward(selected_token, upstream_names, messages)
    
    # 5. 结果回写
    state.record_decision(request_id, original_model, logical_model, ...)
    return response
```

#### 模块 5：New API Adapter（转发/结果解析）
**文件**：`router/adapter.py`  
**职责**：
- 用选定的 token 转发请求到 New API `:3000/v1/chat/completions`
- 流式/非流式响应透传
- 解析结果：
  - 200 → 清错误计数、更新 last_success、记录命中渠道（从 New API 响应或日志解析）
  - **402** → 立即把该 (provider, model) 置 exhausted，事件入库；增强层用下一个候选供应商重试 1 次（唯一允许增强层重试的场景）
  - 500/连接错 → 交给 New API 原生重试；增强层只记账
  - 400 invalid model → 告警（说明 model_mapping 缺了条目）
- 回填 RouterDecisionEvent.final_channel / outcome / newapi_request_id

**关键设计决策（ADR）**：
- 增强层**不直连上游**（红线 2），所有流量必须经 New API
- 重试职责切分：传输层归 New API，额度层归增强层，各重试一次上限可控

### 2.3 模块依赖方向（依赖倒置原则）

```
Request Handler ───→ Model Matcher
               ├──→ State Manager
               ├──→ Decision Engine ───→ Model Matcher
               │                     ├──→ State Manager
               │                     └──→ New API Adapter
               └──→ New API Adapter
```

**规则**：Decision Engine 依赖 State Manager 和 New API Adapter，不反向依赖。  
**效果**：State Manager 可独立测试（mock New API）。

## 三、一次完整请求生命周期

### 3.1 时序图（序列图核心片段）

```
客户端                Smart Router              State Manager         Decision Engine      New API :3000
  │                        │                        │                      │                  │
  │── POST /v1/... ──→ │                        │                      │                  │
  │                        │── ① 令牌校验 + 限流 ──→ │                      │                  │
  │                        │── ② 模型解析 ────────→ │                      │                  │
  │                        │                        │  查 QuotaState       │                  │
  │                        │── ③ 额度决策 ───────────────┼──→ 查 fallback_chain │                  │
  │                        │  选 token-free/paid  │                      │                  │
  │                        │── ④ 转发 ───────────────────────┼──────────────→ POST /v1/... │
  │                        │                        │                      │── 200 / 402 ────→ │
  │                        │── ⑤ 结果回写 ──────────→ 更新状态          │                  │
  │                        │   记录 DecisionEvent    │                      │                  │
  │<── 200 / 402 ────────────────────────────────────────────────────────────────────┘
```

### 3.2 五步决策详细（对应第二节模块）

**① 令牌校验 + 限流窗口**（Request Handler）  
- 校验客户端 Key → 查该 Key 的模型白名单 → 渠道级速率窗口（免费源 60 RPM 保护）

**② 模型解析**（Model Matcher）  
- 点名真实模型 → 容错匹配 → 查 ModelCatalog 得 logical_model + upstream_names
- `auto-free` → 任务类型识别 → 池内选 health_score 最高的模型

**③ 额度决策**（Decision Engine + State Manager，核心）  
- 查 QuotaState(logical_model 的候选供应商)：
  - 免费供应商 available → 选 **token-free**（group=free 逻辑）
  - 免费供应商 exhausted/冷却中 → 按 fallback_chain 选付费供应商 → **token-paid**（group=paid 逻辑）
- 全部不可用 → 明确报错（含"哪些模型也挂了"的信息），不瞎试

**④ 转发 New API**（New API Adapter）  
- 携带选定的 token 转发到 `:3000/v1/chat/completions`
- New API 内部照常执行 priority/weight 路由 + 原生重试（传输层兜底）

**⑤ 结果回写**（New API Adapter + State Manager）  
- 200 → 清错误计数、更新 last_success、记录命中渠道
- **402** → 立即把该 (provider, model) 置 exhausted；增强层用下一个候选供应商重试 1 次
- 500/连接错 → New API 原生重试；增强层只记账
- 回填 RouterDecisionEvent 所有字段

### 3.3 增强层单请求开销预算（架构约束）

| 阶段 | 开销 | 说明 |
|---|---|---|
| ① 令牌校验 | < 1ms | 内存查表 |
| ② 模型解析 | < 1ms | 内存查 ModelCatalog |
| ③ 额度决策 | < 1ms | 内存查 QuotaState（1 次查询） |
| ④ 转发 New API | 网络 RTT | 不计算在增强层开销内 |
| ⑤ 结果回写 | < 2ms | 异步落库（不阻塞响应） |
| **总计** | **< 5ms** | 目标达成（M0 实测 New API 自身 ~1s） |

## 四、FastAPI 编码前最后确认

### 4.1 文件结构（M1-1 骨架）


### 4.2 编码顺序（M1 里程碑）

| 顺序 | 任务 | 对应模块 | 验收标准 |
|---|---|---|---|
| 1 | FastAPI 骨架 + 健康检查 | main.py | `GET /health` 返回 200 |
| 2 | 数据模型 + 数据库初始化 | models.py + state.py | router.db 自动创建，表结构正确 |
| 3 | 模型解析（点名模型） | matcher.py | `GET /debug/resolve?model=glm-5.2` 返回 logical_model |
| 4 | 额度状态内存加载 | state.py | 启动时打印 QuotaState 条数 |
| 5 | 决策引擎（点名模型链路） | decision.py + handler.py | 用 m0-test token 调通 :8000 → 转发到 :3000 → 200 返回 |
| 6 | 结果回写（决策日志） | state.py | RouterDecisionEvent 表有新记录 |

**M1 明确不做**（架构评审决议）：
- ❌ auto-free 虚拟模型（放 M2）
- ❌ cost-portal 成本分析（放 M3）
- ❌ 复杂任务分类（放 P1）

### 4.3 开发约束（红线）

1. **不改 New API 源码**（AGPL-3.0 规避）
2. **不直连上游**（保计费/重试/协议转换）
3. **不直写 New API SQLite**（只走管理 API）
4. **流式透传不碰字节流**（用 FastAPI StreamingResponse）
5. **单请求增强层开销 < 5ms**（内存查询，异步落库）
