## 二、验证一：rkKW5x retry/failover 触发验证 ✅

**目标**：真实故障下，priority 高渠道失败 → retry → 自动进入下一 priority 渠道。

**实验设计**：
- 模型：`deepseek-v4-flash-202605`（ch1 pri=10 与 ch3 pri=5 共有）
- 故障注入：ch1 base_url 改为 `http://127.0.0.1:1/v1/chat/completions`（connection refused，模拟渠道宕机）
- 前置：经管理 API `PUT /api/option/` 设置 `RetryTimes=2`（设置前 options 表无此键，默认不重试）
- 备份：`one-api.db.bak.rkKW5x.20260903_145648`

**要求的五项证据（全部真实采集）：**

| 证据项 | 内容 |
|---|---|
| ① 请求日志 | logs 表新增 `id=729, type=2, ch=3, model=deepseek-v4-flash-202605, pt=84, ct=5, quota=3338` |
| ② 命中渠道 | 首次选中 **ch1**（pri=10 最高）→ 失败；重试命中 **ch3** |
| ③ retry 次数 | RetryTimes=2 生效，消费日志 admin_info 记录 `"use_channel":["1","3"]`（先 1 后 3） |
| ④ 容器日志 channel error | `[ERR] channel error (channel #1, status code: 500): upstream error: do request failed` + `do request failed: ... dial tcp 127.0.0.1:1: connect: connection refused` |
| ⑤ 最终成功渠道 | **ch3（tencent-free）**，HTTP 200 返回正常内容，耗时 1.06s |

**结论**：连接级故障 → 原生重试链工作正常，自动降级到下一 priority 渠道，对调用方透明（200）。ch1 base_url 已恢复原值并复验。

## 三、验证二：deepseek-v4-flash 修复后回归验证 ✅（并发现新问题）

**目标**：plan pri=10 / free pri=5 时，请求 `deepseek-v4-flash` 第一次即命中 plan。

**第一轮 20 次：20/20 全部失败（HTTP 400, no log）** —— 没有掩盖，直接深挖根因。

**根因链（三段取证）：**
1. 容器日志：`channel error (channel #1, status code: 400): invalid model` —— **路由正确，第一次就命中了 ch1（pri=10）** ✅
2. 上游直连对照：腾讯 plan 上游对 `deepseek-v4-flash` 返回 `400 invalid model`；对 `deepseek-v4-flash-202605` 返回 200 —— **plan 上游只认带日期的版本 ID**
3. 单请求完整追踪：ch1 报 400 后日志即终止，**无任何重试/切换动作** —— **400 属不可重试错误**

**这解释了"反转异常"的最终全貌**：昨天看到的"命中 free 而非 plan"，前半段是 ch1 abilities 缺精确名（已修），后半段是**即使进了候选池，plan 上游也不认识这个模型名，400 后又不重试，请求直接死掉**。

**修复**：ch1 配置 `model_mapping = {"deepseek-v4-flash": "deepseek-v4-flash-202605"}`（对外统一名 → 对内真实 ID）。
备份：`one-api.db.bak.dsf_phase2.20260903_150739`

**第二轮 20 次回归：20/20 全中 ch1（tencent-plan），第一次调用即命中，无一例外。**

| 渠道 | priority | 命中 |
|---|---|---|
| ch1 tencent-plan | 10 | **20/20（100%）** |
| ch3 tencent-free | 5 | 0/20 |

**遗留提示**：ch1 其余 11 个模型尚未逐一与 plan 上游核对模型名（本次只确认了 deepseek 系列）。建议 M1 用 `/api/channel/test/1?model=xxx` 批量过一遍（你 15:02 在 Web 界面测 ch3 的操作我已看到，两边无冲突）。

## 五、完整路由机制模型（全量验证后的最终版）

```
请求(model, token.group)
  └→ abilities 表按 (group, model) 精确匹配取候选渠道
       └→ 过滤 enabled=1 且 channels.status=1
            └→ 按 priority 分组，取最高 priority 组
                 └→ 组内按 weight 加权随机选一个渠道
                      ├→ 成功 → 记账（logs type=2）→ 返回
                      ├→ 可重试错误（连接失败/5xx）→ RetryTimes 内重试
                      │    └→ 本组耗尽 → 降到下一 priority 组继续
                      └→ 不可重试错误（400 等）→ 直接失败返回 ❌ 不切换
```

**⚠️ 对 auto-free 的关键风险**：腾讯免费额度耗尽时上游返回什么错误码尚未验证。
- 若返回 400/402 且不重试 → free_first 策略会在额度耗尽时**直接报错给用户**，原生重试链救不了，必须由我们自己的增强层处理
- 若返回 5xx/连接错误 → 原生重试链可直接兜底
- **Module 3 第一个实验：人为打爆一个免费模型额度，观察返回码与重试行为**
