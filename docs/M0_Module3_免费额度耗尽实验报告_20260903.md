## 四、三大结论（用户指定输出项）

### ① 腾讯免费额度耗尽的表现

- **HTTP 402**，`type=gateway_error`，`code=401008`
- 报文特征固定：`free trial quota ... exhausted and postpaid billing is not enabled`
- **可 100% 程序化识别**，无歧义（与 400 无效模型、500 引擎错误均不同）
- 耗尽后请求**零 token 消耗**（上游直接拒绝）

### ② New API 是否自动切换

**部分自动，有关键限制：**

| 行为 | 结果 |
|---|---|
| 402 是否触发重试 | ✅ **触发**（昨日已验证 400 不触发，今日确认 402 触发 3 次尝试）——New API 按错误类型区分 |
| 重试是否跨渠道 | ⚠️ **只在候选池内**：该模型仅 ch3 有 → 3 次全打 ch3 → 依然 402 |
| 结合昨日证据的推断 | rkKW5x 已证明上游 500（连接失败）时重试会**降到下一 priority 渠道**并成功；402 同样可重试 → **若耗尽模型同时挂在 free（高 pri）+ plan（低 pri），402 后重试理论上会自动切到 plan** |
| 耗尽模型是否自动下线 | ❌ **不会**（glm-5.3/minimax-m3 耗尽多日仍 enabled=1），重复调用持续浪费重试次数 |
| 失败是否记账/扣费 | ✅ 不记账、零消耗 |

### ③ 对 Auto Router 架构的影响

**好消息——free_first 故障降级可以纯 New API 配置实现：**
1. 把可耗尽模型同时挂两个候选：free 渠道（priority 高）+ plan 渠道（priority 低）
2. 额度耗尽 → 402 → New API 原生重试 → 降级到 plan → 用户无感
3. **这条主链路不需要增强层拦截**，New API 原生能力覆盖

**坏消息——三件事 New API 做不了，必须增强层（或运营自动化）：**

| 缺口 | 后果 | 增强层职责 |
|---|---|---|
| 无额度查询 API（全部 404） | 无法主动知道还剩多少额度，只能被动等 402 | 被动感知：捕获 402 事件 → 标记该模型额度状态 |
| 耗尽模型不自动下线 | 每次调用都先打 3 次失败重试再降级，延迟增加、日志噪音 | 捕获 402 后自动把该模型从 free 候选池移除/降权 |
| 无额度预警 | 耗尽瞬间才感知 | 结合历史用量做趋势预估（可选，M2+） |

**架构定位结论：增强层不是"救火队"（重试链 New API 自己能走通），而是"额度状态管理者"——感知 402、维护模型额度状态表、动态调整候选池。**
